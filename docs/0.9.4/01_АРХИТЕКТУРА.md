# Chelsy AI 0.9.4 — архитектура (этап 1)

Версия документа: 1 (2026-11-17). Основание: ТЗ «Chelsy AI 0.9.4», редакция 01 (`docs/0.9.4/ТЗ_0.9.4.md`).
Исходный проект: Chelsy AI 0.9.3 (ветка `claude/lucid-feynman-qalnhk`, коммит `18d370e`). Версия 1.0 не объявляется.

## 1. Решения владельца (Приложение Б ТЗ)

| Вопрос | Решение 2026-11-17 | Следствие |
|---|---|---|
| Сеть Host | CGNAT / неизвестно | Прямой доступ из интернета, скорее всего, невозможен. Host диагностирует это (NET-02) и честно объясняет. Без туннелей и посредников. Работает LAN; для внешней сети нужен входящий IPv4/IPv6 от провайдера. |
| Почта | Своей почты нет | Саморегистрация и восстановление по почте **выключены**. Аккаунты создают администраторы локально: первичный пароль и обязательная смена при первом входе (NET-03). |
| Оборудование обучения | NVIDIA ≥ 12 ГБ VRAM | Реальная QLoRA-адаптация 7B-модели на машине владельца. Код, конфиг и seed готовит исполнитель; веса появляются только после запуска на этой машине (MIND-03). |
| Пароли из Supabase | Перенести хеши | Законный SQL-экспорт bcrypt-хешей `auth.users`. Host проверяет bcrypt и при первом успешном входе переводит пароль на Argon2id (MIG-01). |
| Email двух администраторов | При защищённой первичной настройке | Не хранятся в исходниках (ADM-01). |
| Модели телефонов, канал iOS/Windows, юрисдикция, сроки хранения, бюджет | Не заданы | Открытые вопросы. Влияют на этап 7 и раздел ПДн, см. §8. |

## 2. Схема (продуктивный путь)

```
 Windows Client ─┐                        ┌─────────────────── Chelsy Host (один установщик) ───────────────────┐
 Android / iOS ──┼── HTTPS (TLS 1.2/1.3) ─▶ Chelsy Gateway :8443/443  ──▶ Auth / Sessions / RBAC (своя БД)        │
 Браузер-кабинет ┘     собственный адрес  │      │  (cookie+CSRF для веба,   ──▶ API v3: профиль, диалоги, память,   │
                                          │      │   bearer для нативных)        задачи, файлы, события (SSE)       │
                                          │      ▼                                                                │
                                          │  Chelsy Mind: Intent → Router(обучаемый) → Planner → Context/Memory   │
                                          │      → Model Runtime (Ollama, только 127.0.0.1) → Quality Validator     │
                                          │      → Artifact Builder (песочница-процесс) → хранилище файлов          │
                                          │                                                                       │
                                          │  Панель Host (127.0.0.1, отдельный процесс; управляет Gateway)        │
                                          └───────────────────────────────────────────────────────────────────────┘
```

* Наружу открыт **только** HTTPS-порт Gateway. Ollama, SQLite, хранилище файлов, Artifact Builder и панель слушают только `127.0.0.1` или вообще не открывают порт.
* Supabase, Tailscale, Brave/SaaS-поиск и внешний AI API в продуктивном пути отсутствуют (NET-01). Supabase используется только разовым миграционным инструментом (MIG-02).
* Сайт-кабинет и API обслуживаются с одного origin Gateway (WEB-04). Публичные страницы сайта могут оставаться на прежнем хостинге; кабинет работает с origin Host.

## 3. Сеть: что реально возможно (NET-02)

| Условие | Результат |
|---|---|
| Клиент в той же LAN, что и Host | Работает: `https://<имя-или-IP-хоста>:8443`. Нативные клиенты проверяют закреплённый ключ Host (профиль доверия в приложении, без установки сертификата в систему). |
| Внешняя сеть, у Host публичный IPv4/IPv6, проброс порта | Работает. Для браузера нужен доверенный сертификат: домен + ACME (Let's Encrypt — раскрываемая инфраструктура доверия) или свой сертификат владельца. |
| CGNAT, нет входящего адреса | **Прямой доступ из интернета невозможен.** Host определяет это (NAT-PMP/UPnP: WAN-адрес роутера в 100.64.0.0/10 или приватном диапазоне) и объясняет варианты: белый IP/IPv6 у провайдера или работа в LAN. Скрытый туннель не подставляется. |

Диагностика встроена в установщик и панель Host: локальный адрес, WAN-адрес роутера, CGNAT, занятость порта, срок сертификата, видимость порта из LAN.

## 4. Аккаунты, сессии, роли (SEC-02, NET-03, ADM-01)

* Своя БД Host (SQLite, миграция 0.9.4 от схемы 903): `accounts`, `sessions`, `auth_events`, `admin_roster`, `admin_requests`, `admin_audit`, `service_status`.
* UUID пользователей сохраняются из Supabase (MIG-01). Хранилища 0.9.3 уже адресованы ключом `sb:<uuid>`, поэтому данные остаются привязанными.
* Пароли: Argon2id с индивидуальной солью, параметры замеряются на Host и записываются в профиль безопасности. Импортированные bcrypt-хеши Supabase проверяются и перехешируются при входе. Минимум 15 символов, максимум не менее 64; вставка разрешена; локальный список слабых паролей.
* Сессии: access 10 мин, refresh до 30 дней с ротацией и обнаружением повторного использования (отзыв всего семейства). Административная сессия — 15 минут бездействия. Значения настраиваются сервером.
* Веб: HttpOnly + Secure + SameSite=Strict cookie и CSRF-токен; токены не попадают в localStorage. Нативные клиенты: Android Keystore (flutter_secure_storage), iOS Keychain (ThisDeviceOnly), Windows DPAPI.
* Перебор: лимиты на аккаунт+источник, источник и сервис; временные задержки без бессрочной блокировки чужого аккаунта; единая ошибка «неверный email или пароль».
* Роли: `user`, `admin`. Ровно два активных администратора. Смена состава требует подтверждения обоих. Восстановление при утрате обоих — локальная процедура владельца ОС (`ChelsyHost.exe --owner-recover-admin`) с аудитом, без удалённого backdoor.

## 5. Граница приватности (SEC-04)

* Административные API возвращают только служебные поля: email, ID, статус, квоты, число устройств, время активности, тип операции. Нет маршрутов, отдающих диалоги, файлы, память, embeddings или темы задач чужого аккаунта. Проверка владельца идёт в коде сервера на каждом чтении, а не в UI.
* «Войти как пользователь», выпуск токена за пользователя, просмотр пароля — не реализуются.
* Шифрование содержимого: у каждого пользователя свой ключ данных (DEK, AES-256-GCM). DEK обёрнут ключом из пароля пользователя (Argon2id → KEK). Второй обёрнутый экземпляр хранится под **кодом восстановления**: его получает только сам пользователь, администраторам он не известен. Административного escrow-ключа нет.
* Смена пароля пользователем перешифровывает обёртку DEK. Сброс пароля администратором открывает аккаунт, но **не** даёт прочитать старое зашифрованное содержимое: без кода восстановления пользователь получает доступ к аккаунту и новым данным, а старые остаются нечитаемыми. Об этом прямо сообщается.
* Граница гарантии: Host расшифровывает данные в памяти, чтобы модель их обработала. Оператор ОС с правами администратора потенциально может получить содержимое из памяти процесса. Это не сквозное шифрование; защита от оператора ОС требует TEE/confidential computing и не обещается.

## 6. Chelsy Mind и файлы (MIND-01..04)

Компоненты из ТЗ реализуются как отдельные модули пакета `mind/`:

* **Intent Analyzer** — язык, цель, формат результата, ограничения, недостающие данные.
* **Trainable Task Router** — свой обучаемый классификатор (chat / research / document / presentation / spreadsheet) с весами в `models/router/`. У него свой датасет, seed, метрики и хеши.
* **Planner** — короткий план и схема результата; пользователю показываются этапы, а не рассуждения.
* **Policy/Tool Gateway** — права и параметры проверяет код. Модель не получает shell, ФС и админ-API.
* **Artifact Builder** — отдельный непривилегированный процесс: папка задачи, лимиты CPU/RAM/времени, без сети. Генерирует TXT/DOCX/PDF/PPTX/XLSX из валидируемой JSON-структуры. Публикация атомарная, у файла SHA-256, версия и idempotency key.
* **Quality Validator** — язык, полнота, структура, разбор созданного файла валидатором.
* **Обучение** — QLoRA-адаптер для базовой открытой модели (лицензия и происхождение указаны), запуск на GPU владельца. Реестр кандидатов, сравнение до/после на фиксированном наборе, откат.

## 7. Совместимость и переход (MIG-01/02)

* Миграции SQLite только добавочные (904+). Перед применением — автоматическая резервная копия и контрольные количества.
* Клиенты 0.9.3 (Supabase + Tailscale) несовместимы с новым Auth: нужна минимальная версия клиента 0.9.4. Host отвечает старым клиентам понятным сообщением об обновлении.
* Supabase отключается после проверенного переноса, не раньше.

## 8. Открытые вопросы и ограничения среды исполнителя

* Юрисдикция, сроки хранения, модели устройств, канал iOS/Windows-распространения и бюджет не заданы. Соответствие 152-ФЗ/GDPR не заявляется.
* Среда исполнителя — Linux-контейнер без macOS, физических устройств и GPU:
  * нативная iOS-сборка проверяется только в CI на macOS-раннере без подписи;
  * испытания на физическом iPhone/Huawei, обучение LoRA и нагрузочные тесты на настоящем Host выполняет владелец по приложенным инструкциям.
  * Эти пункты отражаются в отчёте как **непроверенные исполнителем**.
