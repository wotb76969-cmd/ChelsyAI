# Chelsy AI 0.9.4 — план миграции с 0.9.3 (MIG-01, MIG-02)

## Порядок

1. **Резервная копия** — `ChelsyHost.exe --backup`:
   * SQLite (`chelsy.db`), конфигурации `%LOCALAPPDATA%\ChelsyAI\*.json`, ключи;
   * проверка `PRAGMA integrity_check`;
   * контрольные количества: аккаунты, диалоги, сообщения, память, документы базы знаний;
   * SHA-256 копии.
2. **Экспорт аккаунтов Supabase** — разовый инструмент `migrate_supabase_accounts.py`, только на машине владельца:
   * SQL через Management API или SQL Editor: `id, email, encrypted_password (bcrypt), email_confirmed_at, created_at, last_sign_in_at, banned_until, raw_user_meta_data->>'display_name'`;
   * файл экспорта шифруется ключом Host (DPAPI) и удаляется после импорта.
3. **Пробная миграция на копии**:
   * миграции 904+ применяются к копии БД;
   * импорт аккаунтов с **теми же UUID**;
   * сверка: каждый `sb:<uuid>` в диалогах/памяти/файлах имеет аккаунт; количества совпадают.
4. **Ввод в эксплуатацию** — та же процедура на рабочей БД после повторной копии; данные, появившиеся после копии, учитываются, потому что миграции добавочные.
5. **Назначение двух администраторов** — `ChelsyHost.exe --setup-admins` (локально, интерактивно):
   * владелец указывает два email;
   * legacy-аккаунт `owner` и прежний `admin_user_id` администраторами автоматически **не** становятся.
6. **Переключение клиентов**:
   * минимальная версия клиента 0.9.4;
   * старым клиентам Host отвечает `426 Upgrade Required` с текстом на русском;
   * окно переключения согласует владелец.
7. **Отключение Supabase** — только после проверенного входа всех перенесённых аккаунтов (или явного решения владельца). До этого Supabase не используется в продуктивном пути, только в шаге 2.

## Пароли

* Хеши Supabase — bcrypt (`$2a$`/`$2b$`). Host проверяет bcrypt и при успешном входе сразу сохраняет Argon2id.
* Политика 0.9.4 требует ≥15 символов. Если перенесённый пароль короче, вход по нему разрешается **один раз**, после чего Host требует смену. Сохранение старого пароля обещается только в этих рамках.
* Если хеш экспортировать не удалось, аккаунт создаётся с тем же UUID и одноразовым паролем, который администратор передаёт пользователю. При первом входе пароль меняется, данные не теряются.

## Ключи шифрования (SEC-04) для существующих данных

* При первом входе после миграции создаётся DEK пользователя, существующее содержимое перешифровывается. Пользователь получает **код восстановления** и сохраняет его сам.
* До первого входа содержимое остаётся в формате 0.9.3: защищено правами ОС и шифрованием диска, но не DEK. Это раскрывается в отчёте.

## Откат

* Миграции 904+ только добавляют таблицы и колонки; откат — восстановление копии из шага 1 (`--restore <файл>`) с повторной сверкой количеств.
* Клиенты 0.9.3 продолжают работать с Supabase до шага 7, если откат выполнен до отключения Supabase.
